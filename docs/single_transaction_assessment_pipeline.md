# Single-Transaction Assessment Pipeline

## Purpose

This pipeline is the first complete vertical slice of the trade-finance copilot. It runs the existing deterministic components in one governed sequence and produces a transaction-level decision brief and action plan.

It does not:

- approve or reject a transaction;
- provide legal advice;
- clear sanctions or AML obligations;
- determine bank credit approval, pricing, limit, or collateral;
- determine K-SURE insurance or guarantee acceptance;
- quote executable FX or financing terms;
- infer missing facts.

## Version 1 scope

Version 1 accepts exactly one approved transaction per `UnifiedCopilotCase`.

This is intentional. Some existing refresh functions replace registry-derived records at the case level. Restricting the first vertical slice to a single transaction prevents records belonging to another transaction from being overwritten or mixed into the current brief.

The governed manifest is stored at:

```text
data/reference/single_transaction_pipeline_v1.json
```

## Stage order

The fixed order is:

1. `trade_document_screening`
2. `document_reconciliation`
3. `transaction_capacity`
4. `product_matching`
5. `transaction_decision_brief`

The final brief always runs. Optional stages are marked `skipped` with a reason when the required reviewed input was not supplied.

## Request contract

`SingleTransactionAssessmentRequest` contains:

- pipeline ID;
- brief ID;
- approved transaction ID;
- selected counterparty ID;
- selected country code;
- explicit document-reconciliation policy;
- optional transaction-capacity request;
- optional explicit trade-finance need profiles;
- maximum number of displayed concerns.

Nested capacity and product requests must reference the same transaction as the pipeline request.

## Preflight controls

Before any stage runs, the pipeline verifies:

- exactly one approved transaction exists;
- its transaction ID matches the request;
- all payment structures belong to that transaction;
- supported trade documents are explicitly linked only to that transaction;
- product profiles and capacity inputs refer to that transaction.

A preflight failure leaves the original case unchanged.

## Stage behavior

### Trade-document screening

Reviewed contracts, purchase orders, and letters of credit are evaluated against the governed clause registry. Findings and risk signals reference approved evidence.

### Cross-document reconciliation

When at least two supported documents are present, reviewed values are reconciled across contract, commercial invoice, and letter of credit. Missing values remain `skipped`, not mismatches.

### Transaction capacity

When an explicit capacity request is supplied, the approved transaction is linked to the selected financial statement, reviewed FX reference, payment structure, explicit protection percentage, and explicit funding need.

### Product matching

When explicit need profiles are supplied, the pipeline refreshes public KB and K-SURE consultation candidates. Only `consultation_candidate` and `insufficient_information` candidates generated by the current run are selected for the final brief. Blocked and non-applicable products remain auditable in the case but are not turned into consultation actions.

### Decision brief

The final stage ranks concerns by the governed severity and category order, reports missing evidence, assigns a pre-screening disposition, and creates dependency-based actions.

## Stage trace

Every stage returns a `PipelineStageTrace` with:

- fixed sequence number;
- stage name;
- `completed` or `skipped` status;
- case hash before and after the stage;
- generated record IDs;
- stage-specific counts and missing inputs.

A completed stage means the deterministic component ran. It does not mean the underlying transaction condition is acceptable or resolved.

## Failure behavior

Execution is fail-closed. A stage exception is wrapped in `TransactionAssessmentPipelineError`, which records:

- failed stage name;
- case snapshot hash at failure;
- original cause.

No partially updated case is returned.

## Idempotency

Running the pipeline again with the same reviewed case and request produces the same final case hash:

- document and reconciliation findings replace stale current results;
- transaction-capacity calculations reuse matching deterministic calculations;
- product candidates refresh from the same registry inputs;
- decision actions replace the current transaction's previous pipeline actions.

## Next engineering unit

The next major step should not add another isolated analysis rule. It should expose this pipeline through a controlled application service and user interface that:

- creates or loads one reviewed case;
- shows source status and missing information before execution;
- requires explicit confirmation for user-entered assumptions;
- displays the brief, top concerns, candidate products, and action dependencies;
- exports an audit-safe JSON package;
- keeps internal hashes and low-level traces in an expandable audit section rather than the primary user view.

Multi-transaction case support should follow only after document, product, and action records carry explicit transaction ownership and case-wide refresh functions are transaction-scoped.
